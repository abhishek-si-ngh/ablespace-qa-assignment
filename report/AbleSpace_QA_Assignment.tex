\section{Test Environment and Setup}

\subsection{Application}

Testing was performed on the AbleSpace -- IEP Goal Tracking App staging application:

\begin{center}
\href{https://staging.ablespace.io}{\texttt{staging.ablespace.io}}
\end{center}

The testing was performed using one manually created test account, as required by the assignment. Fictional student and profile data was used during testing.

\subsection{Primary Test Environment}

\begin{itemize}
    \item Operating environment: Desktop
    \item Primary browser: Google Chrome 154.0.8037.98 (64-bit)
    \item Additional browsers: Mozilla Firefox and Microsoft Edge
    \item Mobile web viewport: 390 $\times$ 844
    \item Tablet emulation: iPad Mini and iPad Pro 13-inch
    \item Testing type: Manual functional, exploratory, validation, usability, and compatibility testing
\end{itemize}

\subsection{Test Data}

The following fictional data was used:

\begin{itemize}
    \item Test user name: Aarav Mehta
    \item Test student: Maya Sharma
    \item School: Green Valley School
    \item Goal: Reading
    \item Goal description: Maya will correctly read simple words with 80\% accuracy.
\end{itemize}

No real student or customer data was intentionally used.

\subsection{Testing Scope}

The following areas were covered:

\begin{itemize}
    \item Account onboarding
    \item Role selection
    \item Email verification
    \item Student creation and editing
    \item Student search
    \item Goal creation
    \item Data collection
    \item Session editing
    \item Activity and History
    \item Collaborator interface inspection
    \item Responsive/mobile web layout
    \item Cross-browser compatibility
    \item Tablet compatibility
\end{itemize}

Security testing, penetration testing, load testing, and performance testing were not performed because they were outside the assignment scope.

\subsection{BUG-001 -- Email Verification Link Fails}

\textbf{Bug ID:} BUG-001

\textbf{Title:} Newly received email verification link displays ``expired or already used''

\textbf{Severity:} High

\textbf{Priority:} High

\textbf{Environment:} \url{https://staging.ablespace.io}, tested 06--07 October 2026

\textbf{Browser / Device:} Google Chrome 154.0.8037.98 (64-bit), Desktop

\textbf{Reproducibility:} Observed once during testing; not retested with a resend

\textbf{Steps to Reproduce:}
\begin{enumerate}
    \item Create an account using fictional test information.
    \item Open the verification email received after account creation.
    \item Click the ``Verify Email'' link.
    \item On the verification page, click ``COMPLETE VERIFICATION''.
    \item Observe the resulting verification status.
\end{enumerate}

\textbf{Expected Result:} The newly received verification link should successfully verify the account and the application should reflect the verified state.

\textbf{Actual Result:} The verification page displayed an error indicating that the request had expired or the link had already been used. The application continued to indicate that the email had not been verified.

\textbf{Impact:} The user cannot complete the normal email-verification workflow using the verification link received immediately after account creation. This affects an important account-level onboarding function.

\textbf{Evidence:}
\clearpage

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.86\textwidth]{images/bug-001-email-verification.png}
    \caption{BUG-001 evidence: Email verification page displaying the ``expired or already used'' message.}
    \label{fig:bug001}
\end{figure}

\noindent
\textbf{Evidence hygiene:} Any verification URL, token, or personal email address should be cropped or hidden before submission.

\noindent
\textbf{Note:} The ability to change the email address from Profile Settings was observed after account creation, but it was not promoted to a bug because the assignment did not establish a requirement that the email address must remain immutable after signup.

\subsection{BUG-002 -- Role Dropdown Accepts Arbitrary Values}

\textbf{Bug ID:} BUG-002

\textbf{Title:} Role dropdown allows arbitrary typed values to become selectable roles

\textbf{Severity:} Medium

\textbf{Priority:} High

\textbf{Environment:} \url{https://staging.ablespace.io}, tested 06--07 October 2026

\textbf{Browser / Device:} Google Chrome 154.0.8037.98 (64-bit), Desktop

\textbf{Reproducibility:} Always during the tested interaction

\textbf{Steps to Reproduce:}
\begin{enumerate}
    \item Open the signup/onboarding flow.
    \item Focus the \textbf{Role} dropdown.
    \item Type an arbitrary value such as \texttt{xyzabc123}.
    \item Observe the options displayed by the control.
    \item Select the arbitrary value.
\end{enumerate}

\textbf{Expected Result:} The Role control should allow selection only from supported/predefined roles, unless custom role creation is explicitly supported.

\textbf{Actual Result:} An arbitrary value such as \texttt{xyzabc123} appeared as a selectable option in the Role control and could be selected.

\textbf{Evidence:}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.84\textwidth]{images/bug-002-role-dropdown.png}
    \caption{BUG-002 evidence: Role control displaying an arbitrary typed value as a selectable option.}

\end{figure}

\noindent
\textbf{Note:} No backend/root-cause assumption is made. The defect is reported from the user-visible validation behavior of the role control.

\textbf{Severity:} Medium

\section{Testing Summary}

\subsection{Testing Performed}

Manual exploratory, functional, validation, usability, and compatibility testing was performed against the AbleSpace -- IEP Goal Tracking App staging application.

The main areas covered were account onboarding, role selection, email verification, student creation and editing, student search, goal creation, data collection, session statistics, session editing, Activity \& History, collaborator interface inspection, responsive web layout, cross-browser compatibility, and tablet emulation.

Desktop checks were performed in Google Chrome, Mozilla Firefox, and Microsoft Edge.

The main workflow was also exercised in Microsoft Edge. Responsive web checks included a 390 $\times$ 844 viewport, iPad Mini emulation, and iPad Pro 13-inch emulation.

\subsection{Issues Found}

Three issues were selected for detailed reporting:

\begin{enumerate}
    \item \textbf{BUG-001} -- the newly received email verification link displayed an ``expired or already used'' error and the application continued to indicate that the email had not been verified. This is the highest-priority issue because email verification is an account-level workflow.
    \item \textbf{BUG-002} -- the Role dropdown allowed an arbitrary typed value to become selectable.
    \item \textbf{BUG-003} -- Session History was difficult to read at the 390 $\times$ 844 mobile web viewport.
\end{enumerate}

One additional input-validation observation was recorded but not promoted to the three primary bugs: the First Name field accepted and saved a numeric-only value. The assignment did not define an alphabetic-only naming rule, so this was not treated as a confirmed defect.

\subsection{Areas Not Tested}

The following areas were intentionally not tested or were only partially inspected:

\begin{itemize}
    \item Security, penetration, injection, load/stress, and performance testing.
    \item Native mobile installation from Google Play Store or Apple App Store.
    \item Native mobile-app behavior of the AbleSpace -- IEP Goal Tracking App.
    \item Billing functionality requiring a Pro subscription.
    \item Sending collaborator invitations.
    \item Creating additional user accounts.
\end{itemize}

These exclusions were made to remain within the assignment rules and avoid unintended external communication or prohibited testing activity.

\subsection{What I Would Test Next}

With another 1--2 hours, I would first retest the email-verification flow using one controlled resend and verify the resulting account state.

I would then expand boundary and validation testing for student and goal fields, test refresh/back-navigation and repeated actions across the main workflow, and perform a broader feature-by-feature compatibility sweep on mobile and tablet sizes.

Finally, I would regression-test the session editing paths and verify that edited session values remain consistent across Data, Capture, Graph, and Stats views.
